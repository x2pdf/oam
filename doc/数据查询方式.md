# 数据查询方式

说明 OAM 如何拉取链上 `input data`，以及主页各 Tab、地址详情页如何组装与筛选结果。与当前代码保持一致，不是设计草案。

日期：2026-08-26

---

## 1. 总览

应用不维护自有交易索引。列表数据有两条路径：

| 路径 | 用于 | 做法 |
|------|------|------|
| Explorer 按地址 | 广场、消息、仅自己、地址数据列表 | 第三方 `txlist` / Blockscout v2，再在本地按 `FetchMode` 过滤 |
| 以太坊 RPC 整块 | 关注 Tab | `eth_getBlockByNumber(..., true)` 拉窗口内全部交易，再在本地筛关注地址 |

统一 Explorer 入口是 `DataSourceManager.fetchAll(address, mode, pageParams)`。  
管理器按「有 API Key 的源 → 无 Key 的源」两档，组内按权重从高到低尝试。**一般源成功（含返回空列表）即结束，不再试下一个。**  
**例外：查询地址是黑洞**时，若本页**过滤后 0 条且没有下一页**，视为软失败并换源。只有**抛错**或上述黑洞空终页才会 failover。单源失败最多再循环 `MAX_DATA_SOURCE_CYCLES`（3）轮；最后一轮仍失败的源会加入本会话 `skipped`，后续请求直接跳过。Explorer HTTP 超时 `DATA_SOURCE_REQUEST_TIMEOUT_MS`（15s）。

当前三个源（权重可在「我的」里覆盖，默认如下）：

| 数据源 | 默认权重 | API Key | 接口 |
|--------|----------|---------|------|
| Routescan | 500 | 否 | Etherscan 兼容 `txlist` |
| Blockscout | 300 | 否 | v2 `addresses/{addr}/transactions`；区间查询走兼容 `txlist` |
| Etherscan | 100 | 是（未填则整源跳过） | Etherscan v2 `account/txlist` |

有 Key 时「有 Key 组」目前只有 Etherscan；它成功返回就不会落到 Routescan / Blockscout。无 Key 时只走 Routescan → Blockscout。

页大小：

| 场景 | 常量 | 默认值 |
|------|------|--------|
| 普通地址 | `DATA_SOURCE_PAGE_SIZE` | 20 |
| 广场黑洞 | `BLACK_HOLE_PAGE_SIZE` | 200 |

广场黑洞过滤后仍为空时，同一轮最多再续拉 `BLACK_HOLE_EMPTY_CONTINUE_PAGES`（3）页（合计最多 1+3 次请求）。

```
广场 / 消息 / 仅自己 / 地址列表
        │
        ▼
DataSourceManager.fetchAll(address, mode, params)
        │
        ├─ 有 API Key 的源（按权重）
        └─ 无 Key 源（fallback）
                │
                ▼
        各 DataSource.fetchMessages
                │
                ▼
        原始交易 → filterTransactionsByMode(mode)
                │
                ▼
        map 成 InputDataItem（带 rawInput）
                │
                ▼
        applyDisplayPipeline（OAMP → UTF-8 → RAW）
                │
                ▼
        UI 本地筛选 + FlatList / 翻页

关注 Tab
        │
        ▼
RPC eth_blockNumber + 窗口内 eth_getBlockByNumber(..., true)
        │
        ▼
filterFollowedWithInput（关注地址 ∩ input 非空）
        │
        ▼
map + applyDisplayPipeline（无解密 client）
```

## 2. FetchMode：按地址拉回之后的本地过滤

在 `transactionMapper.filterTransactionsByMode` 中，先丢掉没有 `input`（或仅为 `0x`）的交易（`ChainTransaction.hasInput`），再按模式过滤。比较用小写地址。

| mode | 调用方 | 保留条件 |
|------|--------|----------|
| `square` | 广场，查询地址固定为黑洞 | `to == 查询地址` |
| `self` | 仅自己 | `from == to == 查询地址` |
| `sent` | 消息「已发出」 | `from == 查询地址` |
| `inbox` | 消息「收到」（`filter` 的默认分支） | `to == 查询地址` |
| `all` | 地址数据列表（含对话） | `from == 地址 \|\| to == 地址` |

这是对**已经按地址拉回的一页交易**做的内存过滤，不是链上专用索引。Explorer 返回的一页里大量无 input 的转账会被丢掉，所以「有下一页」不等于「过滤后还有条目」。

## 3. 各数据源分页与区间能力

### 3.1 Etherscan / Routescan（`etherscanStyle`）

- 请求：`page` + `offset`，`sort=desc`。广场会把 `offset` 设为 200。
- 下一页：若本页**原始** `txlist` 条数 `== offset`，则 `{ page: page+1, offset }`，否则 `null`。判断用的是原始长度，不是过滤后条数。
- Etherscan 还带 `chainid=1` 和 `apikey`。

### 3.2 Blockscout

- 常规分页：v2 `addresses/{addr}/transactions`，query 用 `items_count`（广场为 200）以及上一页返回的 `next_page_params`（拼 query 时丢掉其中的 `filter`、`items_count`、`offset`、`page`）。
- 下一页：透传 API 的 `next_page_params`；没有则为 `null`。
- `fetchOutgoingTransactions` 会额外设 `filter=from`（公钥恢复用，不是列表主路径）。

### 3.3 Explorer 按区块区间（代码有，当前 UI 不用）

若 `params` 同时带合法的 `startblock` 与 `endblock`，三个源都会走 `txlist` 区间拉取（Blockscout 此时也走兼容 `txlist` 而不是 v2 地址接口），最多翻 `fetchEtherscanStyleBlockRange` 的 10 页，结果 `next_page_params` 为 `null`。  
主页和地址列表**不会**传这对参数。

各源还实现了 `fetchLatestBlockNumber()`，管理器也暴露了；**关注页不用它**，而是 RPC `eth_blockNumber`。

### 3.4 关注页：RPC 整块窗口

关注页**不走 Explorer 按地址接口**。

1. `fetchLatestBlockNumberViaRpc()`：`ethers` provider `getBlockNumber()`，带 RPC 节点 fallback。
2. `makeBlockWindow(end, FOLLOWING_BLOCK_WINDOW)`：闭区间 `[end - 99, end]`（窗口 **100** 个区块；代码注释约合主网 20 分钟）。若 `end < 99` 则从 0 起。
3. `fetchBlockWindowTransactions`：对该闭区间每个块 `eth_getBlockByNumber(hex, true)`。JSON-RPC batch 每批 `FOLLOWING_RPC_BATCH_SIZE`（10）个块；节点不支持 batch 时该批拆成单块（并发最多 4）。批与批之间并发 `FOLLOWING_BLOCK_FETCH_CONCURRENCY`（8）。整块请求超时 `FOLLOWING_BLOCK_FETCH_TIMEOUT_MS`（20s），并走 RPC fallback（`cycles: 2`）。
4. 拉齐后 `filterFollowedWithInput`：`hasInput` 且 `from` 或 `to` 落在关注地址集合（小写、去重）。

与关注地址个数无关：始终拉这一窗的全部交易再筛。

## 4. 主页四个 Tab

UI 标签稳定 ID：`square` / `following` / `messages` / `self`。默认从左到右即此顺序；「我的」里可改 `homeTabWeights`（权重大的靠左，同权保持默认次序）。冷启动打开当前最左标签。

内部加载通道仍是固定下标（与 UI 顺序无关）：广场 0、sent 1、inbox 2、仅自己 3、关注 4。消息 Tab 会同时打 sent 与 inbox 两路。

进入主页且筛选状态从存储读完后，四个 Tab **各拉一次**（广场 / 关注 / 消息 / 仅自己）。

### 4.1 广场

只查询黑洞地址 `0x000…000`（`BLACK_HOLE_ADDRESS`），`mode = 'square'`，页大小 200。  
不拉当前用户地址，也不拉关注列表。

- 过滤后：`to == 黑洞` 且 input 非空。意图是公开广播样本，不是全网时间线。
- 本轮过滤后仍无条目且还有下一页时，自动续拉最多 3 页。
- 黑洞终页空会在管理器里换源。
- 单次 `fetchAll` 抛错被 `catch` 成空列表 + `errors`；若最终 0 条且全是错误，提示 API Key 或通用错误。
- 游标就是 Explorer 的 `next_page_params`（存在该 Tab 的 `nextPageParamsRef[0]`）。每次请求强制 `offset` / `items_count` = 200。
- 卡片展示发送方（`InputDataItem.address` / `from`）。发送方是黑洞 / 自己 / 关注列表中的地址时，显示对应短名（黑洞文案、`recipientSelf`、关注备注）。

### 4.2 消息 / 仅自己

- 消息：`fetchAll(profile.address, 'sent' | 'inbox', params)`，两路独立分页。UI 按勾选合并，按 `id`（交易哈希）去重，再按时间倒序。
- 默认勾选「已发出」和「收到」，状态写入 `@oam_filter_state`。
- 仅自己：`fetchAll(profile.address, 'self', params)`。只读钱包不拉解密、只提示无法解密。写钱包未解锁时不展示列表，提示解锁。解锁后用私钥建 `OAMPClient` 跑展示管线；锁屏或离开主页（桌面锁定策略）会把已解密 OAMP 擦成 `OAMP_ENCRYPTED`。

无 `profile.address` 时，消息和仅自己不请求。

### 4.3 关注

关注列表为空：不打 RPC，列表为空。列表变化（地址集合 key 变了）会重新拉关注 Tab。

关注非空时：

1. 首次 / 下拉刷新：RPC 取当前高度 `L`，拉 `[L - 99, L]`（若高度不足则从 0）。
2. 内存筛关注地址收发且 input 非空（可能 0 条）。
3. `nextEndBlock = start - 1`（已到创世则为 `null`）。上滑或空列表点「加载更早」再拉更早的 100 个整块，结果按哈希**追加**到已有列表。
4. 某一窗筛选后 0 条仍算成功，并设置 `followingIgnoreEndReachedRef`，避免 `onEndReached` 自动连扫；用户再拖动列表或点按钮才会继续。

展示前还有一层与拉取相同的 from/to 关注过滤（`displayedFollowingData`）。

### 4.4 广场 / 消息的 UI 二次筛选（不改变拉取范围）

勾选存在 `@oam_filter_state`。默认：广场「全部」关，「纯文本」「OAMP」开；消息两向都开。

广场，在已拉取的 `squareData` 上：

| 勾选 | 行为 |
|------|------|
| 全部 | 直接显示 `squareData`（含 RAW） |
| 纯文本 | `contentKind === 'UTF-8'` |
| OAMP | `to` 为黑洞（`isBlackHoleAddress`），**不**按 `contentKind === 'OAMP'` 过滤 |

未勾「全部」时，纯文本与 OAMP 两路做并集。拉取已限制为发给黑洞，因此勾上「OAMP」实际上会带上该批里所有 `to` 为黑洞的条目（含 RAW），除非关掉 OAMP 只留纯文本。  
勾选「全部」不会多查链上地址。

消息 Tab 只有「已发出 / 收到」，没有「关注」勾选（i18n 里的 `filterSubscribed` 未挂到 UI）。

## 5. 展示管线（拉取之后）

`applyDisplayPipeline` 对每条 `InputDataItem`（单项失败则标 RAW，不抛死整表）：

1. `isOAMP` 且能反序列化头：  
   - `crypto === NONE` 且 payload 可展示 → `OAMP`；payload 失败则 miss，继续 UTF-8。  
   - 加密：无 `client` → `OAMP_ENCRYPTED`。有 client 时仅尝试 **个人笔记**（`MessageType.PERSONAL` 且 `from == to == userAddress`）。P2P 加密在这里不会解密，停在 `OAMP_ENCRYPTED`。  
2. 否则严格 UTF-8 解码 → `UTF-8`。  
3. 否则 → `RAW`（hex）。

只有「仅自己」且钱包已解锁才传入 `OAMPClient`。广场、关注、消息、地址列表的 `client` 均为 `null`。

## 6. 地址数据列表 / 对话

`AddressDataListScreen`，从关注详情进入：

- 查看该地址全部：`fetchAll(address, 'all', params)`，每次加载只拉 **1** 页。
- 对话：同样 `all`，再留 `from/to` 恰好为「该地址 ↔ 当前用户」的条目。过滤后为空且还有下一页时，自动续拉，最多 `MAX_PAGES_PER_LOAD`（10，写在该文件内）。管线不带解密 client。

---

## 7. 翻页（Load More）

主页 `onEndReached`（阈值 0.2）→ `loadData(..., isLoadMore=true)`：

- **广场 / 仅自己 / sent / inbox**：该通道自己的 `nextPageParamsRef`。广场下一页仍强制页大小 200。
- **消息**：sent 与 inbox 各自翻页；页脚「没有更多」要两路游标都耗尽。
- **关注**：游标是下一窗 `endBlock`。空窗会暂时忽略 `onEndReached`。
- 加载更多时按 `id` 与旧列表合并，时间倒序。下拉刷新清空该 Tab 数据与游标后重拉。

地址列表同样 `onEndReached` 翻页；对话模式一次 `fetchPages` 可能已连拉多页。

## 8. 为何广场仍可能很少看到外人广播

不是发给黑洞的交易不会被广场请求（点对点、合约调用、自己/关注的其它交易都不在此列）。

「别人发给黑洞」只依赖黑洞这一路。已做的缓解：单页 200、空页最多再续 3 页、终页空换源。

仍受限于：Explorer 超时与限流、打给零地址的无 input 噪音、没有全链 calldata 索引、以及有 Key 时若 Etherscan 先「成功」返回则不会再用 Routescan/Blockscout。

## 9. 其它相关查询（不是主页列表）

发送加密消息前，`lookupRecipientPublicKey` 用 `fetchOutgoingTransactions` 取该地址历史上的发出交易 hash（只要 `from` 匹配，**不要求 input 非空**），再 RPC 拉完整交易从签名恢复公钥。Blockscout 发出列表带 `filter=from`。最多尝试 8 笔。这与广场/关注列表无关。

## 11. 与代码一致的约束

1. Explorer 只能按地址分页，没有「全网带 calldata 的时间线」API。  
2. 广场 = 发给黑洞且带 input 的样本；不含自己/关注的其它交易。  
3. 普通地址空列表仍算成功；**仅黑洞终页空**会换源。  
4. 广场翻页使用黑洞单游标，页大小固定 200。  
5. UI 筛选只作用于已拉取集合。  
6. 关注页按 RPC 整块窗口（默认 **100** 个区块）拉全量交易，再在本地用关注列表筛选。  
7. 会话内失败源会被 skip，换数据源权重或杀进程前可能一直不再试该源。  
8. 数据源实现了按 `startblock/endblock` 拉区间的能力，但当前主页与地址列表未使用。  
9. Explorer 的 `fetchLatestBlockNumber` 当前无 UI 调用方。
