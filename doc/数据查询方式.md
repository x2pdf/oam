# 数据查询方式

说明 OAM 如何从区块浏览器拉取链上 `input data`，以及主页各 Tab、地址详情页如何组装与筛选结果。

日期：2026-08-25

---

## 1. 总览

应用**不扫全链**，也不维护自有索引。所有列表数据都来自「按以太坊地址查交易」的第三方 Explorer API：

| 数据源 | 默认权重 | 是否需要 API Key | 接口形态 |
|--------|----------|------------------|----------|
| Routescan | 500（较高优先） | 否 | Etherscan 兼容 `txlist` |
| Blockscout | 300 | 否 | Blockscout v2 `addresses/{addr}/transactions` |
| Etherscan | 100（较低优先） | 是 | Etherscan v2 `account/txlist` |

统一入口是 `DataSourceManager.fetchAll(address, mode, pageParams)`。  
管理器按「有 Key 组 → 无 Key 组」两档、组内按权重从高到低尝试；**一般源成功（含返回空列表）即结束**。  
**例外：黑洞地址**在「本页过滤后 0 条且没有下一页」时视为软失败，继续换下一个源（空成功换源）。只有**抛错**或上述黑洞空终页才会 failover。单源失败可多轮重试（`MAX_DATA_SOURCE_CYCLES`）。请求有超时（默认 15s）。

页大小：

| 场景 | 常量 | 默认值 |
|------|------|--------|
| 普通地址 | `DATA_SOURCE_PAGE_SIZE` | 20 |
| 广场黑洞 | `BLACK_HOLE_PAGE_SIZE` | 200 |

黑洞过滤后仍为空时，同一轮最多再续拉 `BLACK_HOLE_EMPTY_CONTINUE_PAGES`（3）页（合计最多 1+3 次请求）。

```
UI（Home / AddressDataList / …）
        │
        ▼
DataSourceManager.fetchAll(address, mode, params)
        │
        ├─ 有 API Key 的源（按权重）
        └─ 无 Key 源（fallback）
                │
                ▼
        各 DataSource.fetchMessages
                │
                ▼
        原始交易列表 → filterTransactionsByMode(mode)
                │
                ▼
        map 成 InputDataItem（仍带 rawInput）
                │
                ▼
        applyDisplayPipeline（OAMP → UTF-8 → RAW）
                │
                ▼
        UI 本地筛选（广场勾选等）+ FlatList 展示 / 翻页
```

## 2. FetchMode：服务端侧「地址关系」过滤

在 `transactionMapper.filterTransactionsByMode` 中，先丢掉没有 `input`（或仅为 `0x`）的交易，再按模式过滤：

| mode | 含义 | 保留条件 |
|------|------|----------|
| `square` | 广场公开广播侧 | `to == 查询地址`（黑洞场景即「发给黑洞」） |
| `self` | 仅自己笔记 | `from == to == 查询地址` |
| `sent` | 已发出 | `from == 查询地址` |
| `inbox` | 收到（默认分支） | `to == 查询地址` |
| `all` | 收发都要 | `from == 地址 \|\| to == 地址` |

注意：

- 过滤发生在**已经按地址拉回的一页交易**之上，不是链上索引查询。
- `square` 与「发给某地址」语义接近；广场里黑洞用 `square`，自己/关注用 `all`。

## 3. 各数据源分页参数

### 3.1 Etherscan / Routescan（`etherscanStyle`）

- 请求：`page` + `offset`（条数），`sort=desc`。
- 下一页：若本页原始条数 `== offset`，则 `{ page: page+1, offset }`，否则 `null`。
- **下一页判断用的是原始 `txlist` 长度，不是过滤后剩余条数。** 因此「一页 20 条原始交易、过滤后 0 条有 input」仍可能认为有下一页。

### 3.2 Blockscout

- 请求：`items_count`（默认等于 `DATA_SOURCE_PAGE_SIZE`）+ 上一页返回的 `next_page_params`（去掉其中的 `filter` 键后拼进 query）。
- 下一页：直接透传 API 的 `next_page_params`；没有则为 `null`。
- 拉「发出交易」时会额外设 `filter=from`（用于公钥恢复等，不是广场主路径）。

## 4. 主页三个 Tab 各自怎么查

主页 `HomeScreen` 内部索引大致为：

| UI Tab | 内部 mode / 行为 |
|--------|------------------|
| 广场 | `square` 组装（多地址并发） |
| 消息 | 同时拉 `sent` + `inbox`，再按勾选合并 |
| 仅自己 | `self` |

### 4.1 广场（核心）

一次加载会构造多路任务，经 `mapPool` 限制并发（`SQUARE_FETCH_CONCURRENCY = 3`）：

1. **黑洞地址** `0x000…000`，`mode = 'square'`，页大小 `BLACK_HOLE_PAGE_SIZE`（200）  
   → 意图：任何人发给零地址、且带 input 的交易（公开广播）。  
   → 若本轮过滤后仍无条目且还有下一页，自动续拉最多 `BLACK_HOLE_EMPTY_CONTINUE_PAGES`（3）页。  
   → 对黑洞：某源返回「终页空」（0 条且无 next）会换源再试。
2. **当前用户地址**（若有），`mode = 'all'`，普通页大小 20  
   → 用户自己相关的收发。
3. **关注列表每个地址**，各自 `mode = 'all'`，普通页大小 20。

合并与分页：

- 各路结果按交易哈希 `id` 去重，按时间戳降序；
- **每个地址独立游标**（`squareCursorsRef`）：`undefined` 表示首页，`null` 表示已耗尽，`object` 为下一页参数；
- 用户点一次「加载更多」时各路用**自己的**游标再进一页（黑洞仍强制带上 200 的 `offset` / `items_count`）；
- 「还有更多」= **任一路**游标非 `null`；已耗尽的地址在 load more 时跳过。

单路失败被 `catch` 成 `{ items: [], errors: [...] }`，不拖垮整次广场加载；若最终完全无条目且全是错误，再提示 API Key 或通用错误。

### 4.2 消息 / 仅自己

- 单地址：`fetchAll(profile.address, 'sent' | 'inbox' | 'self', params)`。
- 「消息」UI 合并 sent + inbox，用勾选「已发出 / 收到」过滤。
- 「仅自己」在钱包解锁时可用私钥建 `OAMPClient` 尝试解密个人笔记；离开或锁屏会擦除已解密内容。

### 4.3 广场 UI 二次筛选（不改变拉取范围）

在已合并的 `squareData` 上：

| 勾选 | 行为 |
|------|------|
| 全部 | 直接显示 `squareData` |
| OAMP | 默认再筛 `to` 为黑洞（`isBlackHoleAddress`） |
| 纯文本 | `contentKind === 'UTF-8'` |
| 关注 | `to` 落在关注地址集合 |

默认通常勾选纯文本 / OAMP / 关注，「全部」默认关。  
**勾选「全部」不会多查链上地址，只会放开本地过滤。**

## 5. 展示管线（拉取之后）

`applyDisplayPipeline` 对每条 `InputDataItem`：

1. 尝试 OAMP（魔数 `OAMP` / `4f414d50`）→ 明文可展示则为 `OAMP`，加密不可读则为 `OAMP_ENCRYPTED`；
2. 否则尝试严格 UTF-8 → `UTF-8`；
3. 否则 → `RAW`。

广场路径一般不带解密 client；解密主要发生在「仅自己」已解锁场景。

---

## 6. 地址数据列表 / 对话模式

`AddressDataListScreen`：

- 普通：对该地址 `fetchAll(address, 'all', params)`，一页一次；
- 对话（带 `peerAddress`）：过滤「仅双方之间」的条目；若过滤后为空且还有下一页，会自动最多续拉 `MAX_PAGES_PER_LOAD`（10）页，避免空刷。

---

## 7. 翻页（Load More）行为

主页列表 `onEndReached` → `loadData(..., isLoadMore=true)`：

- **消息 / 仅自己**：使用该 Tab 的单一 `nextPageParamsRef`。
- **广场**：使用 `squareCursorsRef` 中各地址自己的游标；一次 load more 同时推进仍有下一页的各路；结果按 id 合并后时间倒序。

翻页动作共用，游标内容不共用：黑洞可以是 page/offset=200 的下一页，关注仍是 20 的下一页，互不覆盖。

---

## 8. 为何广场仍可能「很少看到外人广播」

按设计，**外人互相发、且不经黑洞 / 自己 / 关注地址的交易永远不会被请求。**

对「别人发给黑洞」的公开广播，依赖黑洞那一路。当前已做的缓解：

1. 黑洞单页原始条数 200（大于普通 20）；
2. 过滤后空页最多再续拉 3 页；
3. 终页空成功会换源；
4. 各地址独立游标，避免大页参数污染其它地址。

仍受限于：Explorer 超时、限流、主网打给零地址的无 input 噪音占比、以及没有全链索引。  
自己或关注「发给黑洞」仍可能不依赖黑洞查询成功即可出现（来自按发送者 `all` 的那一路）。

## 10. 设计边界（写死的约束）

1. Explorer 只能「按地址」，没有「全网带 calldata 的时间线」API。  
2. 广场 = 黑洞广播样本 ∪ 自己 ∪ 关注，不是全网广场。  
3. 普通地址空列表仍算成功；**仅黑洞终页空**会换源。  
4. 广场翻页动作共用，**游标按地址分离**。  
5. UI 筛选只作用于已拉取集合，不能扩大数据源覆盖面。
