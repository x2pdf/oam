# 广场页智能填充获取、区块缓存与 OAMP 筛选修正

## 问题分析

### 问题 1：固定区块扫描导致空页面
当前 `scanRecentBlocks()` 固定扫描 10 个区块就返回结果。以太坊平均每 12 秒出一个块，10 个区块约 2 分钟，这些区块中可能全部是纯 ETH 转账（input = `0x`），过滤后有效条目为 0，页面显示空白。

现有的自动翻页机制（HomeScreen 第 508-524 行）仅在 `displayedSquareData.length === 0` 时触发一次加载更多，不够健壮。

### 问题 2：OAMP 筛选逻辑错误
当前 `oampFilteredData` 使用 `isBlackHoleAddress(item.to)` 过滤，这与 OAMP 协议无关。正确做法是检测交易的 input data 是否符合 OAMP 协议（magic bytes `0x4f414d50`）。

### 问题 3：无本地缓存，重复请求浪费
每次加载/刷新都重新请求所有区块数据，但区块链历史数据具有不可变性（已确认区块永不改变），完全可以本地缓存避免重复网络请求。

## 改动 1：blockScanner.ts -- 目标填充模式

**文件**: `src/datasource/blockScanner.ts`

**核心思路**: 将 `scanRecentBlocks` 改为循环式扫描，每轮扫描一批区块（`BATCH_SIZE = 50`），累积有效条目达到目标数量（`TARGET_ITEMS = 20`）或扫描区块总数达到上限（`MAX_BLOCKS = 500`）时停止。

### 关键参数
```
TARGET_ITEMS = 20      // 每次加载至少获取的有效条目数
BATCH_SIZE = 50         // 每轮并发获取的区块数
MAX_BLOCKS = 500        // 单次请求最大扫描区块数（安全上限）
```

### 函数签名变更
```typescript
export async function scanRecentBlocks(params?: {
  fromBlock?: number;
  count?: number;       // 保留但语义改为"目标条目数"，默认 20
}): Promise<DataSourceResult>
```

### 算法流程
1. 确定起始区块号（`fromBlock` 或最新区块）
2. 循环：
   - 每轮取 `BATCH_SIZE` 个区块（并发请求 `eth_getBlockByNumber`）
   - 过滤 `hasInput`（input !== '0x' && input.length > 2）
   - 累积到 items 数组
   - **停止条件**（满足任一即停）：
     - `items.length >= TARGET_ITEMS`（填充完成）
     - 已扫描区块总数 >= `MAX_BLOCKS`（安全上限）
     - 区块号 <= 0（已到创世块）
     - 本轮所有请求均失败（网络故障）
3. 返回 items + `next_page_params`（下一轮的 `fromBlock`）

### 错误处理
- 单区块请求失败：静默跳过（`catch(() => ({ result: null }))`），不影响整体
- 连续多轮 0 有效条目但未达 MAX_BLOCKS：继续扫描，不提前终止（可能只是暂时区块段无 input 交易）
- 全部请求失败：返回空 items + error

## 改动 2：新建 blockCache.ts -- 区块缓存模块（基于 MMKV）

**文件**: `src/datasource/blockCache.ts`（新建）

**核心思路**: 利用区块链历史数据不可变性，将已确认区块的 hasInput 交易缓存到本地 MMKV，避免重复网络请求。

### 关键参数
```
CONFIRMATION_THRESHOLD = 20      // 距离最新区块 >= 20 个区块才允许缓存（约 4 分钟，远超实际 reorg 深度）
MAX_CACHED_BLOCKS = 5000         // 最大缓存区块数（约 25 天以太坊历史，~200MB）
MMKV_INSTANCE_ID = 'block-cache' // MMKV 独立实例 ID，与业务数据隔离
KEY_META = 'bc_meta'             // 索引 key：已缓存区块号有序列表
KEY_PREFIX = 'bc_'               // 区块数据 key 前缀，完整 key 为 bc_{blockNumber}
```

### MMKV 实例初始化
```typescript
import { MMKV } from 'react-native-mmkv';

const cacheStorage = new MMKV({ id: 'block-cache' });
```

使用独立 MMKV 实例，与业务数据（AsyncStorage）和敏感数据（SecureStore）隔离，便于独立管理和清除。

### 缓存数据结构
```typescript
// 单区块缓存数据（JSON 序列化后存入 MMKV）
interface CachedBlock {
  blockNumber: number;       // 区块号
  timestamp: number;         // 区块时间戳
  items: InputDataItem[];    // 该区块内过滤后的 hasInput 交易
}

// 索引数据（存储在 KEY_META 中）
interface CacheMeta {
  blockNumbers: number[];    // 已缓存的区块号列表（升序）
  cachedAt: number;          // 最后写入时间戳
}
```

### 存储策略
- 每个区块一个独立 MMKV key：`bc_{blockNumber}` → JSON.stringify(CachedBlock)
- 索引 key：`bc_meta` → JSON.stringify(CacheMeta)
- MMKV 基于 mmap，无单值大小限制，即使包含图片数据的 OAMP 交易（rawInput 几百 KB）也无问题
- **无需分片**，每个区块独立存取，读取和淘汰都是 O(1)

### 对外 API
```typescript
// 查询单个区块缓存（同步，无需 await）
getCachedBlock(blockNumber: number): CachedBlock | null

// 批量查询：返回指定区块范围内已缓存的区块号列表
getCachedBlockNumbers(fromBlock: number, toBlock: number): number[]

// 写入缓存（仅当 blockNumber <= latestBlock - CONFIRMATION_THRESHOLD 时才写入）
setCachedBlock(block: CachedBlock, latestBlock: number): void

// 淘汰超限：当 blockNumbers.length > MAX_CACHED_BLOCKS 时，
// 从列表头部（最小 blockNumber）逐个 delete 对应 key，直到不超限
pruneCache(): void

// 清空缓存（删除所有 bc_ 前缀的 key + meta key）
clearCache(): void
```

### 写入流程
1. `setCachedBlock()` 检查 `blockNumber <= latestBlock - CONFIRMATION_THRESHOLD`
2. 序列化 CachedBlock 为 JSON，写入 `bc_{blockNumber}`
3. 读取 `bc_meta`，将 blockNumber 插入有序列表（如不存在）
4. 写回 `bc_meta`
5. 调用 `pruneCache()` 检查是否超限

### 读取流程
1. `getCachedBlock()` 直接 `cacheStorage.getString('bc_{blockNumber}')`
2. JSON.parse 返回 CachedBlock，不存在则返回 null

### 容量估算
- 每个区块约 60 条 hasInput 交易，JSON 序列化后约 30-40KB
- 含图片的 OAMP 交易可能达到几百 KB/区块，MMKV 无单值限制
- 5000 区块上限 ≈ 150-200MB（约 25 天以太坊历史）
- MMKV 基于 mmap 文件，总容量仅受磁盘空间限制

## 改动 3：blockScanner.ts -- 集成缓存 + 目标填充

**文件**: `src/datasource/blockScanner.ts`

将改动 1 的目标填充逻辑与改动 2 的缓存模块结合。

### 修改后的算法流程
1. 确定起始区块号（`fromBlock` 或最新区块），记录 `latestBlock`
2. 循环：
   - 每轮取 `BATCH_SIZE` 个区块
   - **先查缓存**：对每个区块号调用 `getCachedBlock()`（同步，零延迟），命中的直接用
   - **未命中的区块**：并发请求 `eth_getBlockByNumber`
   - 过滤 `hasInput`，累积到 items 数组
   - **写入缓存**：对已确认的区块（blockNumber <= latestBlock - CONFIRMATION_THRESHOLD）调用 `setCachedBlock()`
   - **停止条件**（满足任一即停）：
     - `items.length >= TARGET_ITEMS`
     - 已扫描区块总数 >= `MAX_BLOCKS`
     - 区块号 <= 0
     - 本轮所有请求均失败（网络故障，且无缓存命中）
3. 返回 items + `next_page_params`

### 缓存命中的优势
- **初始加载**：首次无缓存，正常网络请求
- **下拉刷新**：只需请求缓存范围之后的新区块（旧的直接读缓存），大幅减少请求数
- **加载更多**：如果之前扫描过的区块范围内有缓存，直接读取，只请求新的未缓存区块

## 改动 5：HomeScreen.tsx -- 修正 OAMP 筛选逻辑

**文件**: `src/screens/HomeScreen.tsx`

### 当前代码（第 149-152 行）
```typescript
const oampFilteredData = useMemo(() => {
  if (showSquareAll) return squareData;
  return squareData.filter(item => isBlackHoleAddress(item.to || ''));
}, [squareData, showSquareAll]);
```

### 修正为
```typescript
const oampFilteredData = useMemo(() => {
  if (showSquareAll) return squareData;
  return squareData.filter(item => {
    const raw = item.rawInput;
    if (!raw || raw === '0x' || raw.length <= 2) return false;
    const hex = raw.startsWith('0x') ? raw.slice(2) : raw;
    return hex.toLowerCase().startsWith('4f414d50');
  });
}, [squareData, showSquareAll]);
```

**说明**: 内联 OAMP magic bytes 检测（与 `src/utils/oampHelper.ts` 的 `isOAMP()` 一致）。也可以直接 import `isOAMP` 使用，更简洁：

```typescript
import { isOAMP } from '../utils/oampHelper';

const oampFilteredData = useMemo(() => {
  if (showSquareAll) return squareData;
  return squareData.filter(item => isOAMP(item.rawInput));
}, [squareData, showSquareAll]);
```

## 测试计划

1. **正常场景**: 初始加载，验证返回 >= 20 条有效数据，页面无空白
2. **稀疏区块**: 模拟连续区块无 input 交易的场景，验证扫描器自动跳过继续向后搜索
3. **安全上限**: 验证扫描不超过 500 区块即停止
4. **加载更多**: 下拉触发 `onEndReached`，验证从上次停止的区块继续扫描
5. **OAMP 筛选**: 取消"全部"勾选，仅勾选"OAMP"，验证只显示 OAMP 协议交易（input 以 `4f414d50` 开头）
6. **组合筛选**: OAMP + 关注同时勾选，验证去重并集正确
7. **缓存命中**: 第二次加载相同区块范围，验证不发起网络请求（通过 console.log 或断网测试）
8. **缓存淘汰**: 验证缓存超过 5000 区块后，最旧的区块 key 被正确删除
9. **缓存安全**: 验证距最新区块 < 20 的区块不会被写入缓存
10. **下拉刷新**: 验证刷新时新区块走网络请求，旧区块走缓存
